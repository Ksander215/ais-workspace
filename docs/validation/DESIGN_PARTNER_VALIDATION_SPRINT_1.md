# Design Partner Validation Sprint #1

## Objective

Test the AIS value hypothesis with one real technical user on a concrete problem.

## Target participant

Primary:
- Software Architect
- Solution Architect
- Enterprise Architect

Strong fit:
- multiple systems;
- distributed technical context;
- architectural decisions;
- modernization/migration/transformation;
- historical decisions or handoffs.

Secondary:
- AI/Agent Architect.

## Sprint structure

### 1. Problem discovery

Do not lead with AIS.

Ask:

1. How do you understand an unfamiliar complex system today?
2. Where does the necessary context live?
3. What do you reconstruct manually?
4. How much time/effort does that take?
5. What happens during handoffs or when someone joins the project?
6. Does the same problem affect AI tools or agents?

### 2. Concrete use case

Ask the participant to select one real or realistically representative task.

Examples:
- understand an unfamiliar repository;
- reconstruct architecture;
- understand why a decision was made;
- identify dependencies;
- continue work after a handoff.

### 3. AIS session

Use the existing AIS MVP before proposing new features.

Record:
- input/context;
- questions asked;
- AIS claims;
- evidence;
- user corrections;
- time/effort.

### 4. Critical evaluation

Ask:

- What is wrong?
- What is missing?
- Which claims do you trust?
- Which claims do you not trust?
- What would you still do manually?
- What would make this useful enough to use again?

### 5. Continuation decision

The key signal is:

> Would you use AIS again on another real task?

Stronger signal:

> Can we try this on our real project/repository?

## Evidence output

Capture:

- participant role (no unnecessary personal data);
- problem in their words;
- concrete use case;
- validation result;
- critical feedback;
- continuation decision;
- next action.

## Prohibited interpretation

Do not claim:
- customer;
- Design Partner;
- pilot;
- production use;
- PMF

until the corresponding evidence exists.
